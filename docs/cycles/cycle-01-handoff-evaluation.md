## 2. ALREADY IMPLEMENTED — handoff/review claims checked against the code

Twenty load-bearing claims were checked. **19 verified, 1 imprecise** (handoff §1 spillway sentence, §2.9). One further claim (Cloudflare reset) faithfully repeats provider documentation that live evidence contradicts — treated in §3b, not counted as a text error.

### 2.1 Registry counts — VERIFIED exactly
Review §1 and handoff §1 claim 81 registered models, 72 enabled, 26 enabled $0 entries. Counted directly from `src/registry.json` this session: **81 entries, 72 enabled, 9 disabled, 26 enabled entries with input price = 0 AND output price = 0** (23 public-only-free + 3 private-free). The handoff's "26" is exact.

### 2.2 Groq private-free nonzero prices — VERIFIED
All four Groq entries are lane `private-free` with nonzero prices: gpt-oss-20b $0.075/$0.30, gpt-oss-120b $0.15/$0.60, qwen3.8-27b $0.80/$4.00, qwen3.6-27b $0.60/$3.00 per M tokens. The review's conclusion is the correct one and matches the code: lane is a *data-posture* label (2026-11-09 owner decision); $0 eligibility is computed from prices in `build_candidates` (`src/gateway.py`), never from the lane name. The normal pass pools all client-allowed lanes into one cost-sorted list, so every true-$0 entry precedes every paid entry regardless of lane labels in `clients.json`.

### 2.3 Sort order — VERIFIED
Handoff §1's description of candidate ordering matches `sort_key` in `build_candidates` (`src/gateway.py` ~L430–436): `(estimate_cost(est_tokens, max_tokens//2), -quality_for(task_class), latency_p50_ms or 99_999)` — estimated cost ascending, then task-class quality descending, then latency. Quality is additionally a *floor gate* before sorting (`quality_for(task_class) < required_quality` → skip `quality_below_required`), with required quality rising by classifier level (`REQUIRED_QUALITY[level]` plus governor steering).

### 2.4 Candidate screening order — VERIFIED (context for several claims)
`build_candidates` (`src/gateway.py` L339–438) checks, in order: enabled → sensitive + `spillway_sensitive_excluded` skip (this one binds in *every* pass, including spillway) → premium-only gate → spillway-pass lane restriction → premium gate → `client.lane_allowed` → governor paid-off veto → provider key presence → sensitive wall (normal pass: public-only-free always skipped `sensitive_public_lane`; uncleared paid/premium skipped `sensitive_not_cleared` unless lane is private-free) → `supports_tools` → quality floor → context fit → `is_verified(now)` → `check_provider_limits`. This is the machinery both texts describe as "classification, class-specific quality scores, price-based ordering" — all present and live.

### 2.5 Mid-request failover — VERIFIED, with precision
`FAILOVER_STATUSES = {401, 403, 408, 413, 429, 500, 502, 503, 504}` (`src/gateway.py` L103), and the serve-loop condition is `status in FAILOVER_STATUSES or status >= 400` — so in practice every ≥400 fails over to the next candidate within the request. Timeouts/transport errors skip as `upstream_unreachable`. `DEAD_LANE_STATUSES = {401, 402, 403}` triggers `note_lane_dead` — **alert-only, deduplicated one per model per day; it changes no routing state.** That last fact is the seed of gap (a)-1: the gateway *notices* dead lanes but deliberately does nothing to selection. There is **no Retry-After handling anywhere**: upstream `Retry-After` headers are ignored, and the gateway emits its own `Retry-After: 60` only on a terminal 429.

### 2.6 Streaming failover — VERIFIED pre-commit; one post-commit edge found
`_stream_response` (`src/gateway.py` L1340+): an upstream non-200 fails over before the body is read; tool-call chunks are buffered through `ToolCallAssembler`, validated with `validate_response`, and can escalate *before* anything reaches the client; text commits at the first content chunk, and post-commit text outcomes are log-only by design (`stream_text_log_only:...`; census: 444 such empty-response rows; streamed traffic is 10,679 of 13,927 route rows, 77%). **Edge neither text mentions:** the `except (httpx.TimeoutException, httpx.TransportError)` handler at the bottom of the streaming producer has no committed/finalized guard — a transport error *after* text chunks were already yielded falls through to the next candidate and would append a second model's stream into the same client response. Pre-commit behavior is correct; this is a post-commit integrity hole. Carried into §5 as ADD-06.

### 2.7 Length/no-content same-model retry — VERIFIED, with precision
In `_json_response` (~L1245): on validation failure `length_no_content` where `entry.reasoning` is true and the candidate has not yet been retried, the gateway makes **one same-model retry with doubled budget** (not counted as an escalation). Any other validation failure escalates once to the next candidate at quality+1 (fallback: ≥ current quality); if none exists, the known-invalid answer is served and logged (`validation_failed_no_escalation`; census: 16 rows). Census (Cycle 1 plan D.1): the same-model retry fired 107×; escalations include length_no_content 88, json_mode_parse_fail 52, tool_args_invalid_json 31. Precision the handoff omits: `empty_response` (finish reason ≠ length) gets **no** budget retry even on reasoning entries — the asymmetry aspect D already targets.

### 2.8 Quota accounting — VERIFIED, and the mismatch is exactly as described
`src/quota.py` (394 lines): a SQLite `QuotaStore` with tables `usage_events, alerts, meta, killswitch` — **no cooldown, breaker, or health state anywhere**, confirming the review's weakness #1 at the storage layer. `window_usage(provider, …)` aggregates **by provider only** (actuals only, `estimated=0`); `check_provider_limits(provider, limits, est_tokens, now)` (L295) receives the *evaluated entry's* `limits` dict but checks it against *provider-aggregate* usage — per-entry declarations, provider-wide accounting, precisely the mismatch handoff §1 describes and the review's weakness #2 restates. Windows: rpm/tpm trailing 60 s; rpd/tpd **local calendar day**. Units are requests and input+output tokens only — **no neurons, no pool identity**. Two further facts neither text states: **failed upstream attempts are never recorded as usage events** (estimated usage is recorded pre-call for candidates[0] only; actuals only on a serve), so the quota store holds *no failure memory at all* — failure evidence exists only as skip reasons in `routes.jsonl`; and when TPD exhaustion is detected, `check_provider_limits` fires `note_lane_dead` — again alert-only.

### 2.9 The spillway — handoff §1 IMPRECISE; review accurate
Handoff §1: *"a paid spillway is invoked after the free/regular attempt path is depleted."* This mischaracterizes the mechanism in a way that matters for design. Reality, from `build_spillway_candidates` (`src/gateway.py` L440+) and the serve loops: **paid and premium entries are already inside the normal cost-sorted candidate list and serve in ordinary order whenever the free entries ahead of them fail or are skipped** — there is no separate "free path" that must deplete first. The spillway is a distinct *second selection* that runs only when normal selection produced **zero** candidates, or when every normal attempt failed upstream (engaged at selection time and re-engaged in each serve loop with `exclude_ids` = the attempted set). Its function is not ordering — it is a *ruled relaxation*: it lifts the sensitive-clearance wall and the per-client premium/lane gates as a last resort (owner ruling 2026-11-07), while still binding the excluded flag, enabled/verified status, tool support, quality floor (with an L5→Q4 fallback), context fit, provider limits, key presence, and the governor emergency veto. `spillway_allowed` is false for explicit pins and premium-alias requests — **pins never spill**. Spillway serves are stamped `free_exhausted_paid_fallthrough` (`SPILLWAY_REASON`, L106). The review's phrase "a last-resort paid spillway" is the accurate summary; the handoff's sentence should be corrected wherever it is quoted.

### 2.10 No tool-use quality dimension — VERIFIED
`src/registry.py`: `TASK_CLASSES = (chat, infra, code, reasoning, long-context)` — no tooling class. `supports_tools` is a binary gate, and in the live registry it is **False on zero of 81 entries** — every entry defaults to True, i.e. tool capability is asserted, never measured. `quality_for` falls back to an entry's *minimum* known quality for an unrated class, so a tooling dimension cannot be improvised from existing data. Review weakness #3 and handoff P2 are both correct.

### 2.11 Classification, quality scores, output validation — VERIFIED
Task classification with per-class quality maps (all 81 entries carry complete 5-class quality maps), sensitivity classification with the lane wall (§2.4), and output validation with escalation (§2.7) are all live, as both texts state. The review's caution is also correct and worth repeating: the Cycle 1 plan *documents* the fixes; a proposed plan is not evidence any fix is deployed. None of the P0–P3 items in either text is live today.

### 2.12 The pin path — VERIFIED, including the review's evidence framing
Review §5 cites `gateway.py` L1023–1045; that is the force-insert block. Full mechanics: a requested model is resolved by `Registry.get()` (id OR upstream model string, first hit wins — the F-02 collision class: one entry's model string is another entry's id; exactness holds by file order today, aspect B generalizes the fix). If the resolved entry's lane is not client-allowed, the request is refused 403 (~L909–918) — an authorization layer, not the selection wall. If the pinned entry is not already in the candidate list, it is force-inserted at position 0 when **only** these hold: lane client-allowed, not governor-paid-off for paid/premium lanes, provider key present, and not (sensitive AND `spillway_sensitive_excluded`). It does **not** check: enabled, the sensitive clearance wall, quality floor, context fit, `verified_until`, rate limits, or `supports_tools`. The Cycle 1 probe P-1 (mock upstream, production registry; plan appendix) reproduced six cases: sensitive+pin to a public-only-free entry → served; sensitive+pin to uncleared paid → served; sensitive+pin to uncleared premium → served; sensitive+pin to an excluded entry → **not** served; pin of a *disabled* entry (plain and sensitive) → served. Route-log census: **0 organic occurrences in 13,927 rows (2,429 sensitive)** — latent, not a leak. The review's framing ("a confirmed code-path weakness, not evidence that sensitive data has already leaked") is exactly right. One interaction neither text notes: **sticky runs after the pin block and outranks it** — a sticky match present in the candidate list is moved ahead of the force-inserted pin.

### 3b. Gaps and findings the texts miss or underweight

1. **The Cloudflare reset discrepancy — stated plainly.** Both texts repeat Cloudflare's documented reset: the pricing page states the 10,000-neuron free allocation with *"All limits reset daily at 00:00 UTC"* (verified by fetch this evaluation, §6), and the review's constraint table repeats "resetting at 00:00 UTC." **Our live evidence disagrees with the documentation for this account.** The pool was exhausted on 2026-11-12 (error code 4006 returned verbatim by Cloudflare: the daily free allocation of 10,000 neurons used up; Muse's direct probe ~20:25 MST, recorded in `~/memory/2026-11-12.md`), and Cloudflare routes were still returning 429 at **00:01 and 03:25 UTC on Nov 13 — after the documented reset — with zero intervening successful serves**. A one-shot verification (~17:54 MST Nov 12) likewise found all four new Cloudflare routes plus the control still `upstream_429`. Consumption math from the published neuron weights explains Nov 12's exhaustion (a single ~20k-in/1k-out gpt-oss-120b turn costs ≈700 neurons; ~14 such turns burn the pool), but it does **not** explain zero serves after the documented reset. So: the texts are not wrong about what Cloudflare documents — the documentation and this account's observed behavior currently disagree. What would resolve it, in order of decisiveness: (i) the account's own neuron-usage data from the Cloudflare dashboard or an authenticated usage API (feeds decision D4); (ii) the timestamp of the first successful Cloudflare serve in `routes.jsonl`, which will reveal the reset boundary the account actually experiences; (iii) confirmation that no other consumer shares the account's allocation. Until one of those lands, no design in Cycle 1 should hard-code 00:00 UTC as this pool's `reset_at` — aspect E's ledger must treat reset times as *observed* data, not documentation.

2. **Reasoning-token telemetry is absent (Cycle 0 F-07 → aspect D).** Neither text mentions reasoning tokens at all. `_usage_from_response` (`src/gateway.py` L237) extracts prompt/completion tokens and cached tokens, but **not** `completion_tokens_details.reasoning_tokens`, and the route record has no such field. Consequences: reasoning burn is invisible (the research line "flag any entry whose reasoning:visible ratio exceeds ~5×" is unimplementable today), the doubled-budget retry in §2.7 flies blind, and aspect D's entire effort/budget program depends on landing this telemetry *first* — which the plan already sequences and the texts' silence should not be allowed to de-prioritize.

3. **`verified_until` is set on 0 of 81 entries (aspect B).** The `is_verified(now)` gate in `build_candidates` is therefore vacuous — nothing is ever unverified — and nothing in the system writes the field. Both texts talk about verification *process* (probes before enabling) but neither notices the registry already has a freshness field that is uniformly empty. Aspect B/F1 close this by making the pin battery the writer (probe records in the quota store; automation never edits the registry directly).

4. **`spend_alert_usd` is armed on only 1 of 7 premium entries (aspect B).** Only `premium/gpt-5.5` ($20.0) has a spend alert; four enabled premium entries (deepseek-v4-pro, glm-5.3, muse-spark-1.1, muse-spark-1.2) have none. Neither text mentions premium spend alerting. Aspect B's invariant battery already requires premium entries to set `spend_alert_usd`; this evaluation confirms the violation count from the live registry.

5. **Sticky-session interaction with cooldown/demotion — unexamined in both texts.** Neither text mentions sticky sessions at all. The design interaction is real: sticky reorders within the filtered candidate list and invalidates when its model is ineligible, so a circuit-open skip composes safely *if* the breaker is implemented as a selection filter (plan E's shape: skip reason `circuit_open` on route rows). But two behaviors need explicit criteria, not assumptions: a demoted-but-not-open sticky model (demotion is a sort penalty — should the stick survive it?), and re-sticking after recovery. Carried into §5 as ADD-03. Note also §2.12: sticky outranks the pin force-insert today, which any G-aspect pin ruling must preserve or deliberately change.

6. **J-2 breaker-authority conflict — the plan governs.** Handoff §3 and §6 describe breakers and demotion as *acting on routing* (mark unavailable, skip the pool, proceed to paid). The Cycle 1 plan ships aspect E **observe-only** — shadow week first, enforcement only after Jordan rules J-2 — and the improvement-loop charter puts enforcement authority with Jordan. **Where they conflict, the Cycle 1 plan and charter govern**: they are Jordan's own project documents, and the handoff itself defers in its §9 (research + design only, no authorization implied). The review does not address the authority question at all. This evaluation therefore maps every breaker/demotion recommendation in §4 to "build under E, enforce only on J-2."

7. **Post-commit streaming transport edge.** §2.6: a transport error after text chunks have been yielded falls through to the next candidate and would append a second model's output to a committed stream. Neither text's streaming discussion (§2H of the handoff) covers it. TEST-11 as written would catch it; no existing test does. Criterion ADD-06.

8. **Provider-reported cost is discarded.** `_usage_from_response` ignores provider-reported cost fields (e.g. OpenRouter/HF `usage.cost`); all costing is recomputed from registry prices. Aspect C's reconciliation (capture `provider_cost_usd` on route rows; close F-06 from a week of rows or the first HF invoice) has no counterpart in either text — their price-truth discussion is catalog-side only. (This is capture-for-reconciliation only; Jordan has ruled the cache-pricing *correction* "not necessary," and nothing here re-opens that.)

9. **The scoring/disable evidence machinery already sketched in the plan is absent from both texts.** `nightly_scoring` (telemetry stub) already computes per-model×class success and proposes quality decrements; aspect E's nightly disable-**proposal** job (failure ≥15% over ≥50 serves/7d, pin-battery failure in 2 rounds ≥24 h apart, or account-dead >24 h — proposals only, never auto-applied; decision J-4) is the governed path from evidence to disablement. The texts propose disable/quarantine outcomes without this evidence standard; adopt their goals, keep the plan's standard.

10. **Shadow/live divergence on pins.** Aspect F.3.4 records that the shadow path lacks the pin force-insert, so shadow replays cannot validate pin behavior — relevant because handoff §6 leans on shadow evaluation before enforcement. The divergence is decision-dependent on J-1 and is already tracked in the plan; neither text notices it.

### Added criteria (Given/When/Then)

- **ADD-01 — Spillway sensitive-wall ruled behavior.** *Given* a sensitive request and all eligible free candidates exhausted or failed, *when* selection falls to the spillway pass, *then* a non-excluded paid/premium entry may serve under the ruled relaxation, an entry flagged `spillway_sensitive_excluded` never serves, and a public-only-free entry never serves a sensitive request in any pass.
- **ADD-02 — Pin/premium parity.** *Given* a client without premium lane access, *when* it pins a premium entry by id or by model string, *then* the request is refused (403) exactly as the premium alias is; and *given* any pinned request whose pinned entry fails upstream, *when* failover proceeds, *then* it proceeds through ordinary candidates and never engages the spillway pass.
- **ADD-03 — Sticky invalidation on demotion.** *Given* a conversation stuck to model M, *when* M's circuit opens (or M is demoted below eligibility) mid-conversation, *then* the next turn serves from the next eligible candidate without an upstream attempt on M, the stick is invalidated with a reason on the route record, and after M recovers the conversation may re-stick.
- **ADD-04 — $0 ordering under partial pool demotion.** *Given* pool X demoted or exhausted and pool Y live, *when* a request is classified, *then* Y's eligible $0 entries are all attempted before any paid entry, and skip reasons on the route record name the pool scope (`pool_id`), not only the model.
- **ADD-05 — Reasoning-burn visibility.** *Given* a response whose usage includes `completion_tokens_details.reasoning_tokens`, *when* the route record is written, *then* it carries `reasoning_tokens` (null when the provider does not report it), nightly aggregation can flag reasoning:visible ratio outliers, and a same-model budget retry does not double-count the first attempt's reasoning tokens.
- **ADD-06 — Post-commit stream integrity.** *Given* a streaming response that has already yielded text chunks to the client, *when* the upstream connection then fails with a transport error, *then* the stream terminates with an error indication and no second model's output is appended; *given* instead a tool-call stream still buffered pre-commit, *when* validation fails, *then* whole-response failover to the next candidate remains permitted.
- **ADD-07 — Demotion never dead-ends selection.** *Given* every candidate for a class demoted or circuit-open, *when* a request arrives, *then* demotion acts as an ordering penalty and the best demoted candidate still serves (with its state visible on the route record) rather than the request failing solely because of breaker state.
- **ADD-08 — Pool-suppression scope precision.** *Given* a `pool_exhausted` signal scoped to a provider's free pool, *when* subsequent requests are selected, *then* that provider's paid entries remain eligible; and *given* a credential-scope signal (401), *then* all entries sharing that credential are suppressed regardless of lane. Scope is taken from the signal — including OpenRouter's `limit_source` — never inferred from the status code alone.

**Added criteria: 8 (ADD-01..ADD-08).**
